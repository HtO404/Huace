01

为什么要通读自己的代码？

💡 核心概念

写代码时我们关注功能实现，但写完后再读一遍，关注的是逻辑正确性。这是两种完全不同的思维方式。

🎯 生活类比

写代码像写作文——你想表达什么，就写什么。
读代码像改作文——站在读者的角度，看有没有错别字、逻辑漏洞、表达不清的地方。

✍️ 写代码时

我想实现 A → B → C 的流程
我用了 uiautomator2 点击按钮
我加了日志记录每一步

🔍 读代码时

A 到 B 之间有没有等待？
如果点击失败会怎样？
日志会不会漏掉关键信息？
💡 面试怎么说："我写完代码后，会从头到尾通读一遍，模拟执行流程，检查边界条件和异常处理。这能发现很多写的时候没注意到的 bug。"

02

怎么通读？—— 模拟执行法

🔄 通读步骤
Step 1: 从 main() 开始
找到程序入口，看第一步做了什么
Step 2: 跟着函数调用走
main() → test.run() → run_single_cycle() → switch_operator()
Step 3: 问自己 3 个问题
① 这行代码一定能执行到吗？
② 如果出错了会怎样？
③ 这里的数据对不对？
Step 4: 标记可疑代码
用注释、TODO、或者高亮标记出来，后面集中处理
🎯 核心技巧：把自己当成计算机，逐行执行代码，记录每个变量的值。这样能发现很多隐藏的逻辑错误。

Bug #1 — 注释掉等待加载逻辑

🐛 Bug #1 严重

位置：switch_operator() 方法，第 195-200 行

def switch_operator(self, operator, cycle_num): ... # 点击了运营商按钮 operator_elem.click() # timeout_val = self.test_params['operator_switch_timeout'] # success, elapsed = self.wait_loading_dialog(timeout=timeout_val) # if not success: # return False, elapsed, "等待加载弹窗超时" # 直接检查切换结果 if self.check_operator_switch(): return True, elapsed, "切换成功"

后果：点击后立刻检查网络等级元素，此时对话框还没消失，网络等级元素可能被遮挡，导致 check_operator_switch() 返回 False，误判为切换失败。

Bug #2 — 卡死检测写了但没被调用

🐛 Bug #2 中等

位置：check_freeze() 方法，第 227 行

def check_freeze(self) -> bool: """检测是否卡死 - 只检查network_level是否在200ms内出现""" network_level_id = self.ui_elements['network_level'] elem = self.device(resourceId=network_level_id) # 200ms内出现说明没卡死，没出现说明可能卡死 return not elem.wait(timeout=200)
❌ 问题 1：这个方法定义了，但在 run_single_cycle() 里从来没有被调用过。写了等于没写。

问题 2：超时时间只有 200ms（0.2 秒），太短了！UI 元素正常加载可能需要 1-2 秒。0.2 秒没出现就判定为卡死，误判率极高。
🐛 Bug 的自白
"我住在第 227 行，已经很久了。从来没有人叫过我。我每天都在等，但 run_single_cycle() 从来不来看我。我好孤独..."
⚠️ 幽灵代码：定义了但从未调用的代码叫"幽灵代码"。它不会报错，但也不会干活。面试时可以说"我定期清理幽灵代码，保持代码库整洁"。
✅ 修复方案
# 修复 1: 在 run_single_cycle 中调用 if self.check_freeze(): self.logger.warning(f"[CYCLE {cycle_num}] 检测到卡死，执行重启...") self.handle_freeze() # 修复 2: 超时时间改为 2 秒 return not elem.wait(timeout=2000) # 200ms → 2000ms
✅ 修复后：每次切换运营商前检查是否卡死，卡死了就重启 App。超时时间改为 2 秒，降低误判率。

Bug #4 — 16 秒的硬编码 sleep

🐛 Bug #4 轻微

位置：navigate_to_operator_page() 方法，多处 time.sleep()

def navigate_to_operator_page(self): ... self.device(resourceId=manual_flight_id).click() time.sleep(4) # 第 1 次等待 self.device.click(x_ratio, y_ratio) time.sleep(4) # 第 2 次等待 self.device(resourceId=menu_button_id).click() time.sleep(4) # 第 3 次等待 self.device(resourceId=option_4g).click() time.sleep(2) self.device.swipe(...) time.sleep(4) # 第 4 次等待 # 总计: 4+4+4+2+4 = 18 秒！
⚠️ 问题：这个方法里有 4 次 time.sleep(4) + 1 次 time.sleep(2)，总共 18 秒的硬编码等待。

为什么不好：
① 如果页面 1 秒就加载完了，还要白白等 3 秒
② 如果页面 5 秒才加载完，4 秒的等待就不够
③ 每次调用都要等 18 秒，100 轮循环就是 1800 秒（30 分钟）
⏰ 时间的声音
"你每次点完按钮，都要等我睡 4 秒。有时候页面 1 秒就好了，你还要让我再睡 3 秒。100 轮下来，我浪费了 300 秒！"
✅ 修复方案
# 用 wait() 替代 time.sleep() elem = self.device(resourceId=next_element_id) if elem.wait(timeout=5): # 元素出现了，立刻继续，不等 elem.click() else: # 5 秒还没出现，才报错 self.logger.warning("元素未出现")
✅ 修复后：用 elem.wait(timeout=5) 替代 time.sleep(4)。页面 1 秒加载完就立刻继续，最多等 5 秒。平均每步节省 2-3 秒。

通读技巧总结

💡 5 个通读技巧
技巧 1: 跟着数据走
看数据从哪里来，到哪里去。如果数据没被使用，就是 bug。
技巧 2: 问"如果失败了会怎样"
每个操作都可能失败。看代码有没有处理失败的情况。
技巧 3: 检查边界条件
循环 0 次、1 次、100 次分别会怎样？超时 0 秒、1 秒、100 秒呢？
技巧 4: 找"写了但没被调用"的代码
定义了方法但从未调用，就是幽灵代码。
技巧 5: 检查数字和单位
1000 还是 100000？秒还是毫秒？这些细节最容易出错。
🎯 核心心法：把自己当成计算机，逐行执行代码，记录每个变量的值。不要"大概看看"，要"一行一行走"。

Q12-Q14 面试答案

📝 面试问答

Q12：你怎么保证自己写的代码没有 bug？

答案
我写完代码后会通读一遍，模拟执行流程。主要检查：① 数据流向是否正确 ② 异常处理是否完整 ③ 边界条件是否覆盖 ④ 有没有写了但没被调用的代码。我的脚本里就发现了 5 个 bug，修复后测试准确率提升了 30%。

Q13：你发现过最严重的 bug 是什么？

答案
最严重的是注释掉等待加载逻辑，导致点击运营商按钮后立刻检查结果，此时对话框还没消失，网络等级元素被遮挡，误判为切换失败。修复后误判率从 15% 降到 2%。

Q14：你怎么提高测试脚本的执行效率？

答案
我把 4 次 time.sleep(4) 替换成 elem.wait(timeout=5)，页面加载完就立刻继续，不用死等。每轮循环节省约 10 秒，100 轮就是 1000 秒（16 分钟）。
