# Using Superpowers — Reasonix Code 版

## 核心规则

> 如果觉得有哪怕 1% 的可能性某个技能适用，就**必须**调用该技能。
>
> 如果某个技能适用于当前任务，你没有选择。你必须用它。
>
> 这不是可选的。你不能理性化绕过它。

## Reasonix Code 中的技能调用

Reasonix Code 中技能通过 `run_skill` 工具或 `/skill <name>` 斜杠命令调用。

当在 `.reasonix/skills/` 下找到技能时，Reasonix Code 读取 SKILL.md 并作为指令跟随。

## 工作流程

```
收到用户消息
    │
    ▼
┌─────────────────────────────┐
│ 是否有技能可能适用？          │
│ （哪怕只有 1% 的可能）        │
└──────────┬──────────────────┘
           │
    ┌──────┴──────┐
    ▼             ▼
  有            没有
    │             │
    ▼             ▼
┌──────────┐  ┌──────────┐
│ 调用技能   │  │ 正常响应  │
│ run_skill │  │          │
└────┬─────┘  └──────────┘
     │
     ▼
┌──────────┐
│ 严格遵守  │
│ 技能指令  │
└──────────┘
```

## 红旗——你在理性化绕过

| 想法 | 现实 |
|------|------|
| "这只是个简单问题" | 问题也是任务。检查技能。 |
| "我需要更多上下文" | 技能检查在澄清问题**之前** |
| "我先看一下代码" | 技能告诉你**怎么**看 |
| "这个不需要正式技能" | 如果有技能就用 |
| "这个技能太大材小用了" | 简单的事也会变复杂 |
| "我先做这一件事" | 做事**之前**先检查 |
| "我知道什么意思" | 知道概念 ≠ 使用技能 |

## 技能优先级

当多个技能可能适用时：

1. **流程技能优先**（brainstorming, debugging）— 决定**怎么**做
2. **执行技能其次**— 指导具体操作

示例：
- "构建 X 功能" → brainstorming 先，writing-plans 第二
- "修这个 bug" → systematic-debugging 先

## 技能类型

- **刚性技能**（TDD、debugging）：严格遵守。不要因为"觉得不必要"就跳过纪律。
- **柔性技能**（patterns）：根据上下文适配原则。

技能本身会告诉你属于哪种。
