# Superpowers Writing Plans — 写实现计划

## 概述

写全面的实现计划，假设执行者对代码库零上下文。记录他们需要知道的一切：每个任务要修改的文件、代码、需要检查的测试和文档、如何测试。

**核心原则：** 每步是一个动作（2-5 分钟），粒度要小到不会出错。

## 使用方式

Reasonix Code 中，计划可以走两条路：

1. **`submit_plan`（推荐）** — 使用内置计划工具，自带步骤列表和进度追踪。适合需要主人审批的复杂任务。
2. **写计划文档** — 保存到 `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`，然后由 subagent-dev 技能执行。

## 范围检查

如果规格涵盖多个独立子系统，应分解为独立计划——每个子系统一个。每个计划应产生可工作、可测试的软件。

## 文件结构

在定义任务之前，映射哪些文件将被创建或修改：

- 用清晰边界和定义好接口的设计单元
- 你能放进脑子里的代码你推理得最好。偏好更小、专注的文件
- 遵循已有模式。不相关的不重构

## 小粒度任务

**每步是一个动作（2-5 分钟）：**
- "写失败的测试" — 一步
- "运行确保它失败" — 一步
- "写最少代码让测试通过" — 一步
- "运行确保测试通过" — 一步
- "Commit" — 一步

## 计划文档头部

```markdown
# [功能名] 实现计划

**目标：** [一句话描述]

**架构：** [2-3 句话描述方法]

**技术栈：** [关键技术和库]

---
```

## 任务结构

```markdown
### 任务 N：[组件名]

**文件：**
- 创建：`path/to/file.py`
- 修改：`path/to/existing.py`
- 测试：`path/to/test_file.py`

- [ ] **步骤 1：写失败的测试** [具体代码]
- [ ] **步骤 2：运行测试验证它失败** 命令 + 预期
- [ ] **步骤 3：写最少的实现代码** [具体代码]
- [ ] **步骤 4：运行测试验证它通过** 命令 + 预期
- [ ] **步骤 5：Commit**
```

## 无占位符

每步必须包含执行者需要的实际内容。永远不要写：
- "TBD"、"TODO"、"稍后实现"
- "添加适当的错误处理"（没有具体代码）
- "类似于任务 N"（重复代码）
- 引用任何任务中未定义的类型、函数或方法

## 自审

写完完整计划后，检查：
1. **规格覆盖：** 每个需求都有对应任务吗？
2. **占位符扫描：** 有 "TBD"、"TODO" 吗？
3. **类型一致性：** 前后使用的函数名/属性名一致吗？

## 执行移交

保存计划后，用 `todo_write` 创建任务追踪列表，或：

- **走 `submit_plan`** — 用内置步骤追踪，主人可见进度
- **走 `superpowers-subagent-dev`** — 每个任务派发 subagent 执行
- **直接顺序执行** — 逐个完成任务，完成后标记
