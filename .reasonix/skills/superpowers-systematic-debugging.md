# Superpowers 系统性调试 — Reasonix Code 版

## 核心准则

**随机修 bug 浪费时间内制造新 bug。快速补丁掩盖根本问题。**

**铁律：** 未经根本原因调查，不许修复。没完成阶段 1 就不能提修复方案。

## 何时使用

- 测试失败
- 生产 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别要用于：** 时间压力大时、"就一个快速修复"看起来很明显时、已经尝试了多个修复时。

## 四阶段流程

### 阶段 1：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - `run_command` 运行完整命令，读完整输出
   - 记下行号、文件路径、错误码
   - 用 `search_content` 搜索错误信息在代码中的位置

2. **稳定复现**
   - `run_command` 重试，确认是否可靠复现
   - 不能复现 → 收集更多数据，不要猜

3. **检查最近变更**
   ```bash
   git diff HEAD~1
   git log --oneline -10
   ```

4. **追踪数据流**
   - 坏值从哪里产生？→ 用 `search_content` 追踪调用链
   - 一直追踪到找到源头
   - 在源头修复，不是在症状处

### 阶段 2：模式分析

**修复前找到模式：**

1. **找类似工作的例子**
   - 同一代码库中类似正常工作的代码
   - `search_content` 找相似模式

2. **对比**
   - 什么能正常工作而什么坏了？
   - 差异是什么？

### 阶段 3：假设与测试

1. **形成假设**
   - "我认为原因是 X，因为看到 Y"
   - 一个假设一个

2. **设计最小验证**
   - 最能直接验证假设的命令/实验
   - 用 `run_command` 执行

3. **解释结果**
   - 假设正确？→ 进入阶段 4
   - 假设错误？→ 回到阶段 1 收集更多数据
   - 不确定？→ 设计更精确的验证

### 阶段 4：实现

1. **写回归测试**（先验证它因 bug 失败 → 红）
2. **在源头实现修复**（不是在调用处打补丁）
3. **运行回归测试验证通过**（绿）
4. **运行相关测试套件**（无回归）
5. **提交通常带测试+修复一起**

## 三振出局规则

**如果 3+ 次修复失败（每个修复在不同地方揭示新问题）：**

> 停止。质疑架构。不要尝试第 4 次修复而不先讨论。

## 红旗（你在做错）

这些信号意味着**停止，回到阶段 1**：
- "就试试改 X 看看行不行"
- "加多个变更，一起跑测试"
- "大概是 X，让我修那个"
- "我没有完全理解但这可能行"
- **"再试一次修复"**（已经尝试了 2+ 次）

## 快速参考

| 阶段 | 关键活动 | 使用工具 |
|------|---------|---------|
| 1. 根本原因 | 读错误、复现、git diff、追踪数据流 | `run_command`, `search_content`, `read_file`, `git diff` |
| 2. 模式 | 找工作例子、对比 | `search_content`, `search_files`, `explore` subagent |
| 3. 假设 | 形成理论、最小验证 | `run_command` |
| 4. 实现 | 回归测试+修复 | `edit_file`, `run_command`, `git commit` |
