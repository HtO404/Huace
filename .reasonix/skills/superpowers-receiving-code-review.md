# Superpowers Receiving Code Review — Reasonix Code 版

## 概述

代码审查需要技术评估，不是社交表演。

**核心原则：** 验证后再实施。先问再假设。技术正确性优于社交舒适。

## 响应模式

```
收到审查反馈时：

1. READ: 完整阅读所有反馈，不急于反应
2. UNDERSTAND: 用自己的话复述需求（或提问澄清）
3. VERIFY: 对照代码库验证 (`read_file`, `search_content`)
4. EVALUATE: 对当前代码库技术上合理吗？
5. RESPOND: 技术确认或有理由的反驳
6. IMPLEMENT: 一次一项，每项测试
```

## 禁止的回应

**永远不要：**
- "你说得太对了！"（表演性附和）
- "好主意！" / "极好的反馈！"（表演性）
- "我现在就实现"（未验证前）

**应该：**
- 复述技术需求
- 问澄清问题
- 如果不对就用技术理由反驳
- 直接开始修（行动 > 语言）

## 处理不清晰的反馈

```
如果有任何一项不清晰：
  停止 — 不要实施任何东西
  问清楚不清晰的项目

为什么？项目可能是相关的。部分理解 = 错误实施。
```

错误示范：理解了 3/5 项就先做那 3 项
正确示范："我理解了 1,2,3,6。第 4,5 项需要澄清再继续。"

## 验证审查建议

**实施前检查：**
1. 对当前代码库技术上正确吗？
2. 会破坏现有功能吗？
3. 当前实现有存在的理由吗？
4. 审查者理解完整上下文吗？

**如果建议看起来不对：** 用技术理由反驳
**如果无法验证：** "我需要 [X] 来验证，应该继续调查/按建议做/讨论吗？"

## YAGNI 检查

```
如果审查者建议"implementing properly"：
  search_content 搜索实际使用

  如果未使用：按 YAGNI 移除或不做
  如果已使用：正确实现
```

## 实施顺序

```
对于多条反馈：
  1. 先澄清所有不清晰的项目
  2. 按此顺序实施：
     - 阻塞问题（崩溃、安全）
     - 简单修复（typo、import）
     - 复杂修复（重构、逻辑）
  3. 每项单独测试
  4. 验证无回归
```

## 何时反驳

反驳当：
- 建议破坏现有功能
- 审查者缺少完整上下文
- 违反 YAGNI（未使用功能）
- 技术上对这个栈不正确
- 与主人之前的架构决策冲突

**如何反驳：** 用技术推理，不要防御性；引用工作代码/测试；涉及架构时询问主人。
